# UTILITI x ARJO HK

# 早期发布 - 范围定义

2 个月构建 | 2 名开发人员 | 覆盖全部 3 类用户群  
版本 1.0 | 2026 年 5 月  
保密

**本文档目的：**本文档定义 Arjo HK 早期发布版本的已确认范围。文档列出所有纳入范围的功能及其清晰说明，所有有意删减的功能及删减原因和目标发布版本，为适配 2 名开发人员、2 个月周期而做出的 4 项有意删减，以及每类用户在上线第一天能够完成的操作。

## 1. 发布背景

| 参数 | 决策 |
| --- | --- |
| 目标客户 | Arjo Hong Kong - 医疗设备服务运营 |
| 发布目标 | 替代当前纸质、电话、Excel 流程。初期预计会并行运行，直到员工建立信心。 |
| 时间线 | 从开发启动起 2 个月 |
| 团队规模 | 2 名开发人员，按并行工作流推进 |
| 范围内用户群 | 全部三类 - 后台协调员、现场工程师、医院员工 |
| 主要工作流 | 新设备安装 + 维修 + 预防性维护，完整组合 |
| 地图服务商 | Google Maps，国际标准 |
| 移动应用 | 工程师 App - 原生 iOS + Android，使用 React Native。医院员工 - 移动端响应式网页表单，不做原生 App。 |
| 智能功能 | 包含 1 个 beta 功能：自然语言服务手册问答。位置功能属于核心功能，不是 beta。 |
| 本文档范围 | 纳入范围的功能 + 有意删减项 + 上线首日用户体验 |

**医院 App 决策：**医院员工使用移动端响应式网页进行故障上报，而不是原生 App。这可减少约 1-2 周原生 App 开发工作，并免除应用商店提交流程。故障上报体验在功能上完全一致：员工点击链接、填写表单、上传照片、提交。原生医院 App 将在 G2 构建。

## 2. 纳入范围的功能

以下每项功能均已确认纳入 Arjo HK 早期发布范围。位置功能以 `⊕` 标记。唯一的智能 beta 功能以 `[Beta]` 标记。

### A. 工单管理 - 5 项功能

**✓ A-01 工单创建 - 全部三种类型**  
后台办公室创建安装、维修和预防性维护工单。字段包括：设备、医院、优先级（普通/紧急）、计划日期、工单描述。每种类型都有自己的工作流路径。

**✓ A-02 工单状态机与审计轨迹**  
API 强制执行严格的状态流转：Created -> Assigned -> In Progress -> Completed，并包含 Paused、Resumed、Urgent、Timer Anomaly、Cancelled 等分支。每一次状态变更都会记录操作者、时间戳和备注。审计日志不可变。

**✓ A-03 手动分配工程师**  
后台协调员从列表中选择工程师，并设置计划日期和时间。工程师会立即在手机上收到推送通知。

**✓ A-04 NFC 扫描开始/结束工单 - 核心差异化能力**  
工程师用手机轻触设备上的 NFC 标签以开始工单 - 计时器启动，GPS 锁定，医院地理围栏激活。再次轻触以结束 - 计时器停止，GPS 确认位于地理围栏内，服务记录提交。从标签读取的 `uid` 必须与工单的 `asset_id` 匹配，否则本次轻触会被拒绝。

**✓ A-05 工单暂停与恢复（零件短缺）**  
工程师在 App 中报告零件短缺 - 工单自动进入 Paused 状态。后台办公室会在短缺队列中看到该工单。零件到货后，后台办公室确认并重新排期。工程师收到恢复通知。

### B. 资产与设备管理 - 7 项功能

**✓ B-01 已安装资产登记 - CRUD**  
后台办公室为每一台安装在 Arjo HK 医院的实体设备创建并维护记录：产品型号、序列号、医院、楼层和房间、安装日期、保修到期日。该记录会在安装工单之前创建，确保工程师到场时拥有完整上下文。

**✓ B-02 NFC 标签启用（写入）**  
在新设备安装过程中，工程师将资产 UUID 写入设备上的空白 NFC 标签。App 构建 NDEF payload `{uid, v:1}` 并写入。系统记录启用时间和工程师。所有新设备安装均必须执行。

**✓ B-03 NFC 扫描获取设备信息**  
扫描已启用设备的 NFC 标签时，会返回完整设备记录、当前未关闭工单、最近 3 条服务记录、合同覆盖状态，以及产品规格 PDF 链接。工程师 App 和医院网页故障表单均可使用。

**✓ B-04 NFC 标签更换流程**  
如果标签损坏或无法读取，工程师可通过序列号手动搜索资产。后台办公室远程确认身份。工程师用相同 UUID 写入新的空白标签。更换事件会被记录。

**✓ B-05 产品目录**  
所有 Arjo 产品型号在交付前预先加载。工程师可查看型号名称、标准零件清单、规格 PDF 链接和默认 PM 周期。工程师只读。后台办公室可以新增或编辑型号。

**✓ B-06 PM 日期自动计算**  
维护工单完成后，系统自动计算下一次 PM 到期日（完成日期 + 产品 PM 周期月数），并写入资产记录。对于新安装设备，首次 PM 日期从安装日期开始计算。

**✓ B-07 指定工程师分配**  
每项资产都可以设置默认指定工程师。为该资产创建维护工单时，系统会自动填入分配工程师。后台办公室可随时覆盖。

### C. 合同管理 - 3 项功能

**✓ C-01 医院合同 CRUD**  
后台办公室为每家 Arjo HK 医院创建并维护服务合同：合同编号、类型（全包/部分/仅紧急）、开始和结束日期、响应 SLA 小时数、客户经理、主要联系人。这是所有计费决策的基础。

**✓ C-02 合同覆盖范围配置**  
后台办公室手动配置每份合同覆盖哪些设备型号和零件，并将每项标记为合同内（不收费）或合同外（可计费）。提交服务记录时，系统自动应用计费标记 - 工程师无需手动判断。

**✓ C-03 合同到期预警**  
合同到期前 30 天（可配置），后台仪表板显示预警面板，列出即将到期的合同。避免覆盖范围意外失效。

### D. 服务手册 - PDF 与 AI 搜索 - 2 项功能

**✓ D-01 产品规格 PDF 上传与存储**  
后台办公室为每个 Arjo 产品型号上传制造商服务手册 PDF。文件存储在 S3 兼容存储中。工程师可在 App 中下载和阅读。交付前预先加载。

**✓ D-03 自然语言服务手册问答 - [Beta]**  
扫描设备 NFC 后，工程师可以用普通英语输入问题，例如：“如何更换吊架组件？”或“安全工作载荷是多少？”系统使用向量嵌入搜索 PDF，并返回最相关的前 3 个章节、页码和一键导航。如果 PDF 已预下载，则可离线使用。

### E. 成本管理 - 3 项功能

**✓ E-01 服务端自动成本计算**  
人工成本自动计算：NFC 计时器时长（分钟）÷ 60 × 工程师档案中的小时费率。API 永远不接受客户端提交的总额。所有成本数据均由服务端计算。

**✓ E-02 间接费用记录**  
工程师记录里程（按配置的每公里费率自动换算）和餐费（受每日上限限制）。每条记录都需要收据照片。可在工单进行中或完成后于 App 中记录。

**✓ E-03 零件使用与自动计费判定**  
工程师从目录选择使用的零件并输入数量。系统自动根据医院合同核对每个零件，并生成分类明细：合同内（吸收成本）与可计费。工程师无需做手动计费判断。

### F. 工程师管理与位置 - Google Maps - 5 项功能

**位置技术栈：**本版本包含 4 项位置功能，全部基于同一套 Google Maps + GPS 基础设施。它们是核心功能，不是 beta。合在一起，它们为后台办公室提供纸质系统无法比拟的实时运营可视性。

**✓ F-01 工程师档案管理**  
后台办公室维护所有 Arjo HK 工程师档案：姓名、员工 ID、等级、小时费率、里程费率、餐费上限、资质认证和分配区域。这些值会直接进入成本计算。

**✓ F-02 GPS 上班打卡/下班打卡**  
工程师在工作日开始时通过 App 上班打卡 - 这会激活 GPS 追踪。工作时间内每 2 分钟发送一次 GPS ping。下班打卡会停止追踪。位置数据保留 30 天后自动清除。

**⊕ F-03 后台实时地图 - Google Maps - 位置功能**  
后台地图同时显示两个实时图层：（1）所有 Arjo HK 医院位置，以图钉显示 - 绿色表示有效合同，琥珀色表示 30 天内到期，灰色表示已过期。（2）所有活跃工程师，以实时 GPS 点显示，并使用状态颜色 - 绿色 = 在现场工作，蓝色 = 路途中，黄色 = 空闲/可用，红色 = 计时异常，灰色 = 下班。点击任意工程师点，会显示姓名、当前工单和状态。点击医院图钉，会显示该地点的所有资产和未关闭工单。

**⊕ F-04 医院地理围栏 + 计时异常提醒 - 位置功能**  
当工程师通过 NFC 轻触开始工单时，系统会在医院周围激活 200 米地理围栏。如果工程师 GPS 显示其在工单计时器仍运行时离开此边界，则启动 5 分钟倒计时。5 分钟后：向工程师发送推送通知（“仍在现场？请轻触 NFC 关闭工单”），后台办公室收到计时异常提醒，其中包含工程师姓名、工单和最后已知位置。

**⊕ A-07 机会型 PM 提醒 - 位置功能**  
当工程师 GPS 确认其位于某医院现场，并且该医院有设备将在 N 天内 PM 到期（可在系统配置中配置，默认 2 天）时，后台办公室会收到实时提醒：“工程师 [Name] 位于 [Hospital] - [Device] 将在 2 天后 PM 到期。现在分配？”后台办公室可批准并立即创建及分配 PM 工单，避免额外现场拜访。系统不会自动创建工单 - 必须由人工确认。

### G. 故障上报 - 3 项功能

**医院员工 - 移动网页，而非原生 App：**医院员工通过移动端响应式网页访问故障上报，而不是下载 App。他们在手机浏览器中打开链接。对于此用例，体验与原生 App 相同 - NFC 扫描识别设备、表单自动填充、上传照片、提交。无需安装应用商店 App。

**✓ G-01 医院员工故障上报 - 移动网页**  
医院员工在手机上打开 Utiliti 网页链接。他们轻触故障设备上的 NFC 标签 - 表单自动填充设备详情。他们添加故障描述、选择严重程度（低/中/高/严重）、上传照片并提交。后台办公室会立即看到报告。

**✓ G-02 后台办公室手动录入故障**  
当医院通过电话报告故障时，后台协调员手动创建故障报告：选择医院和设备、输入问题描述，并可从同一页面立即生成维修工单。

**✓ G-03 故障状态追踪**  
医院员工可通过网页查看任何已提交故障报告的状态（Received -> Engineer Assigned -> In Progress -> Resolved）。无需打电话询问进度。

### H. 零件与库存 - 3 项功能

**✓ H-01 零件目录与库存管理**  
后台办公室维护 Arjo HK 零件目录：零件编号、名称、单位成本、供应商。库存数量手动更新。当库存低于配置的最低值时，仪表板显示低库存提醒。

**✓ H-02 零件短缺报告与工单暂停**  
工程师在 App 中选择不可用零件并提交短缺报告。工单自动进入 Paused 状态。后台办公室短缺队列实时更新，显示哪些工单正在等待哪些零件。

**✓ H-03 零件到货确认与工单恢复**  
后台办公室在系统中标记零件已到货。系统标记所有正在等待这些零件的暂停工单。后台办公室可立即重新排期或设置未来日期。工程师收到工单恢复推送通知。

### I. 报表 - 2 项功能

**✓ I-01 核心运营报表**  
后台办公室可查看：按状态统计的工单总数、按工单类型统计的平均解决时间、首次修复率，以及每名工程师完成的工单数 - 可按日期范围筛选。可导出为 PDF 或 CSV。

**✓ I-02 单工单成本视图**  
每个工单详情页显示完整成本明细：人工（由 NFC 计时器计算）、间接费用（里程 + 餐费）和零件（合同内 vs. 可计费）。当前阶段没有单独报表导出 - 可在工单记录中查看。

### J. 系统配置与通知 - 4 项功能

**✓ J-01 系统参数配置**  
后台办公室配置：里程费率（每公里）、餐费上限（每日）、PM 提前提醒窗口（默认 2 天）、地理围栏半径（默认 200 米）、地理围栏提醒倒计时（默认 5 分钟）、合同到期预警（默认 30 天）、Google Maps API key。

**✓ J-02 用户与权限管理**  
后台办公室管理所有 Arjo HK 系统用户：后台员工、工程师和医院联系人。分配角色（admin、coordinator、engineer、hospital_user）。管理工程师档案（等级、费率、资质认证）。

**✓ J-03 推送通知**  
实时推送通知发送到工程师 App（iOS + Android），用于：新工单分配、工单状态变化、零件到货、地理围栏提醒。医院员工通过浏览器通知接收故障报告状态变化。

**✓ J-04 WebSocket 实时更新 - 后台办公室**  
后台办公室无需刷新页面即可接收实时更新：工单状态变化、工程师 GPS 更新（地图点实时移动）、短缺报告、PM 到期提醒、地理围栏提醒。由 Laravel Echo 驱动。

## 3. 有意删减项 - 及原因

为了让 2 个月、2 名开发人员的时间线可实现，本版本有意排除了 4 类功能。所有删减功能都已记录其目标发布版本。

**删减原则：**每一项删减都是为了保护核心价值主张。NFC 工单流程、实时地图、自动成本计算和合同计费均保持完整。被删减的内容要么 AI 负载较重，要么需要历史数据才有意义，要么会增加完整 App 部署工作。所有删减都不影响 Arjo 使用本版本运行日常运营。

### Cut 1 - 医院原生 App -> 移动网页

不构建完整原生 iOS/Android 医院 App，医院员工通过移动端响应式网页进行故障上报。对用户而言，体验在功能上相同 - 点击链接打开页面，通过设备 NFC 扫描（Android 使用 Web NFC API，iOS 使用手动搜索）、填写表单并提交。

| 项目 | 说明 |
| --- | --- |
| 节省时间 | 约 1-2 个开发人周 |
| 损失内容 | 医院员工无法收到后台推送通知（他们通过打开链接查看状态）。iOS 无法通过网页使用 NFC 自动填充（改为手动设备搜索）。 |
| 目标发布 | 双平台完整 NFC 的原生医院 App -> G2 |
| 风险 | 低 - 医院员工交互频率较低。网页表单满足需求。 |

### Cut 2 - 自然语言合同查询 -> G2

员工和工程师用自然语言询问合同覆盖范围的能力（例如“这个零件是否在 Queen Mary Hospital 合同覆盖范围内？”）已从本版本删减。合同覆盖仍会自动执行 - 计费判定逻辑完整纳入范围。被删减的是其上的对话式 AI 界面。

| 项目 | 说明 |
| --- | --- |
| 节省时间 | 约 1-2 个开发人周（合同数据向量索引 + 对话 API） |
| 损失内容 | 员工必须在后台办公室查看合同记录以核对覆盖范围。自动计费标记仍然工作 - 工程师不受影响。 |
| 目标发布 | 自然语言合同查询 -> G2 (C-05) |
| 风险 | 低 - 计费判定是自动的。仅异常查询需要手动查看。 |

### Cut 3 - 合同 PDF 自动解析 -> G2

上传新合同时，AI 驱动的关键字段提取（覆盖型号、零件、SLA、到期日）已删减。合同数据由后台协调员手动录入。考虑到 Arjo HK 上线时的合同量，这可管理。

| 项目 | 说明 |
| --- | --- |
| 节省时间 | 约 2 个开发人周（Python FastAPI 微服务 + PDF 解析 + 字段提取模型） |
| 损失内容 | 合同需要手动录入，而非 AI 辅助提取。对于少量合同，每份合同约 30 分钟。 |
| 目标发布 | 合同 PDF 自动解析 -> G2 (C-04) |
| 风险 | 上线时低。如果合同量显著增长，会变成摩擦点。 |

### Cut 4 - 详细成本报表与导出 -> G2

成本数据（人工、零件、费用）会完整计算，并显示在每个工单详情页。删减的是专用多维成本报表 - 可按工程师、医院或合同期间筛选并导出 PDF/CSV。核心 I-01 运营报表仍纳入范围。

| 项目 | 说明 |
| --- | --- |
| 节省时间 | 约 0.5-1 个开发人周（报表构建器、筛选逻辑、导出格式） |
| 损失内容 | 上线时没有聚合成本报表导出。成本可按单个工单查看。财务团队在首个周期需要手动汇总。 |
| 目标发布 | 带导出的多维成本报表 -> G2 (E-04, I-02 enhanced) |
| 风险 | 试点阶段低。Arjo HK 财务团队可在前 2-3 个月使用工单级数据。 |

## 4. 每类用户上线首日可获得什么

以下是系统上线后，三类 Arjo HK 用户从第一天起即可完成的事项。

### 后台协调员

- 创建和管理所有工单类型 - 安装、维修、PM。
- 在实时 Google Map 上查看所有工程师 - 谁在哪里、正在做什么，实时可见。
- 医院图钉一眼显示合同状态 - 绿色、琥珀色或灰色。
- 如果工程师在工单计时器仍运行时离开医院，接收地理围栏提醒。
- 当工程师已经在现场时，收到 PM 机会提醒。
- 处理零件短缺 - 查看队列、确认到货、重新排期。
- 查看每个已完成工单的成本明细 - 不再需要手动计算。
- 合同计费自动处理 - 标准工单无需查表。
- 追踪所有故障报告，从打开到解决。

### 现场工程师

- 在手机上接收工单分配，包含完整设备和医院详情。
- 在设备上轻触 NFC 开始 - 计时器自动启动。
- 轻触后立即获得设备历史、合同状态和规格 PDF。
- 用普通英语询问设备手册问题 - 即刻获得相关章节。
- 记录使用的零件 - 计费状态自动判定。
- 随手记录里程和餐费 - 需要收据照片。
- 轻触 NFC 结束工单 - GPS 确认，记录提交。
- 无需打电话给办公室即可报告零件短缺。
- 即使医院 WiFi 较弱也能使用 - 关键操作会排队并同步。

### 医院员工

- 在任意手机上打开 Utiliti 链接 - 无需下载 App。
- 轻触故障设备上的 NFC 标签（Android），或按设备名称搜索。
- 设备详情自动填充 - 只需描述故障并添加照片。
- 30 秒内完成提交。
- 随时查看故障报告状态 - 不再需要打电话给 Arjo 询问进度。
- 查看其医院所有设备及最近服务日期。

## 6. 反馈收集计划

本次早期发布的目的，是让 Arjo HK 开始使用系统并产生结构化反馈，从而驱动 G2 优先级排序。以下问题应在上线后前 4-6 周结束前得到回答：

| 领域 | 需要收集的反馈问题 | 询问对象 |
| --- | --- | --- |
| NFC 工作流 | 在 Arjo 使用的设备上，轻触开始和结束工单是否可靠？是否存在 NFC 读取不稳定的医院环境？ | 工程师 |
| 工单派发 | 分配工单的时间是否减少？手动分配流程是否足够快，还是需要更早上线位置推荐功能？ | 协调员 |
| 实时地图 | Google Maps 视图在日常运营中是否有用？医院图钉和工程师点是否提供了协调员此前缺失的可视性？ | 协调员 |
| 地理围栏提醒 | 提醒触发是否正确？是否存在误报？200 米半径是否适合 Arjo HK 医院场地？ | 协调员 + 工程师 |
| 成本计算 | 基于 NFC 的人工成本是否准确？费用类别是否足够，还是需要其他间接费用类型？ | 工程师 + 财务 |
| 合同计费 | 标准工单的自动计费标记是否正确？是否存在系统无法处理的覆盖范围边界案例？ | 协调员 + 财务 |
| 手册搜索问答 | 工程师是否在使用自然语言搜索？最常出现哪些问题？对于 Arjo 的具体设备，答案准确度如何？ | 工程师 |
| 医院网页表单 | 移动网页表单是否足够，缺少原生 App 是否造成摩擦？Android 上浏览器 NFC 扫描是否可靠？ | 医院员工 |
| 并行运行 | 还有哪些事项仍在与系统并行使用纸质或 Excel 完成？为什么？要实现完全替代还需要改变什么？ | 所有用户 |

**G2 优先级决策：**上线后 4-6 周，应与 Arjo HK 举行复盘会议，产出下一批 G2 功能的排序清单。上述反馈问题的答案将决定位置感知排程推荐、原生医院 App 或合同 PDF 自动解析中，哪一项是最高优先级新增能力。
